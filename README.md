## What is an RV32I ALU?

An **Arithmetic Logic Unit (ALU)** is a purely combinational circuit that forms the computational core of a processor's Execution (EX) stage. In the RISC-V RV32I Base Integer Instruction Set, the ALU executes arithmetic, logical, shift, and comparison operations on two 32-bit word inputs.

* **Inputs:**
* **`A[31:0]`** — First 32-bit operand (Register `rs1` or Program Counter `PC`).
* **`B[31:0]`** — Second 32-bit operand (Register `rs2` or Sign-Extended Immediate).
* **`alu_op[3:0]`** — 4-bit operation control code generated by the processor control unit.


* **Outputs:**
* **`Y[31:0]`** — 32-bit primary computation result.
* **`zero`** — 1-bit branch evaluation flag (driven high when `Y == 0`).



```
                +-----------------------+
    A [31:0] ==>|                       |
    B [31:0] ==>|       alu_rv32i       |==> Y [31:0]
alu_op [3:0] ==>| (Combinational Core)  |==> zero
                +-----------------------+

```

## ALU Operation Encoding

The 4-bit `alu_op` control input routes execution to specific computational functional units:

| `alu_op` | Name | Description | Equation / Expression |
| --- | --- | --- | --- |
| `0000` | **ALU_ADD** | 32-bit Addition | $Y = A + B$ |
| `0001` | **ALU_SUB** | 32-bit Subtraction | $Y = A - B$ |
| `0010` | **ALU_SLL** | Shift Left Logical | $Y = A \ll B[4:0]$ |
| `0011` | **ALU_SLT** | Set Less Than (Signed) | $Y = (A <_{\text{signed}} B) ? 1 : 0$ |
| `0100` | **ALU_SLTU** | Set Less Than (Unsigned) | $Y = (A <_{\text{unsigned}} B) ? 1 : 0$ |
| `0101` | **ALU_XOR** | Bitwise XOR | $Y = A \oplus B$ |
| `0110` | **ALU_SRL** | Shift Right Logical | $Y = A \gg B[4:0]$ (Zero-filled) |
| `0111` | **ALU_SRA** | Shift Right Arithmetic | $Y = A \ggg B[4:0]$ (Sign-extended) |
| `1000` | **ALU_OR** | Bitwise OR | $Y = A \mid B$ |
| `1001` | **ALU_AND** | Bitwise AND | $Y = A \ \& \ B$ |

## Detailed Architecture & Working Principle

The module `alu_rv32i` is constructed as a continuous combinational network. The design avoids instantiating redundant logic blocks by sharing internal datapath structures:

```
                     A [31:0]            B [31:0]
                        |                   |
                        +----+         +----+
                             |         |
                     +-------v---------v-------+
                     | 33-bit Subtractor Helper |
                     +------------+------------+
                                  |
                                sub_res
                                  |
                +-----------------+-----------------+
                |                                   |
     +----------v----------+             +----------v----------+
     |  SLT Signed Logic   |             |  SLTU Unsigned Logic|
     | (Overflow Protected)|             |    (A < B Check)    |
     +----------+----------+             +----------+----------+
                |                                   |
                +-----------------+-----------------+
                                  |
                                  v
+-------------------------------------------------------------------+
|               Multiplexer / Case Statement Execution              |
|   Selects output based on alu_op [3:0] (ADD, SUB, SLL, Logic...)  |
+-------------------------------------------------------------------+
                                  |
                                Y [31:0]
                                  |
                   +--------------+--------------+
                   |                             |
                   v                             v
               Y Output                   Zero Flag Logic
               [31:0]                     (Y == 0 ? 1 : 0)

```

### 1. Shared Subtractor Datapath

Instead of building distinct subtractor and magnitude comparator structures, a single 33-bit helper wire calculates subtraction with sign extension:


$$\text{sub\_res} = \{1'b0, A\} - \{1'b0, B\}$$




### 2. Signed Comparison (`SLT`) & Overflow Handling

Direct subtraction ($A - B$) can cause 32-bit signed integer overflow when comparing numbers with opposite signs (e.g., maximum positive `0x7FFFFFFF` minus a negative number `-2`). To prevent erroneous comparison outputs, the ALU evaluates the sign bits of inputs `A` and `B` first:

* If $A[31] \neq B[31]$, the negative number is smaller ($A[31]$ dictates the result directly).
* If $A[31] == B[31]$, overflow cannot occur, and the sign bit of the subtraction result (`sub_res[31]`) safely indicates whether $A < B$.

$$\text{slt\_val} = (A[31] \neq B[31]) ? A[31] : \text{sub\_res}[31]$$




### 3. Shift Operations & Operand Truncation

In the RISC-V RV32I ISA, 32-bit registers can only be shifted by 0 to 31 bit positions ($2^5 = 32$). The ALU explicitly truncates the shift magnitude to the lowest 5 bits of operand `B` (`B[4:0]`):

* **Logical Shift Left (`SLL`):** Zero-fills from the right.
* **Logical Shift Right (`SRL`):** Zero-fills from the left.
* **Arithmetic Shift Right (`SRA`):** Preserves the sign bit $A[31]$ during right-shifting via SystemVerilog's `$signed()` system function.

### 4. Zero Flag Generation

The `zero` output flag acts as a comparator for branch instruction evaluation (such as `BEQ` or `BNE`). It continuously evaluates whether all bits of result `Y` are zero:


$$\text{zero} = (Y == 32'h0000\_0000)$$

## Timing Constraints & Delay Derivation

Because the ALU is pure combinational logic with no real clock input, a **virtual clock** (`virt_clk`) is instantiated in the Xilinx Design Constraints (`constraint_alu.xdc`) file to establish pad-to-pad path delay boundaries:

```xdc
create_clock -name virt_clk -period 20.000
set_input_delay  -clock virt_clk 2.000 [get_ports {A[*] B[*] alu_op[*]}]
set_output_delay -clock virt_clk 2.000 [get_ports {Y[*] zero}]
```


### Mathematical Delay Calculation

The worst-case propagation path through a 32-bit combinational ALU runs from the input ports, through the ripple/carry adder chain of the subtractor, across the multiplexer tree, and down through the 32-bit `OR`-reduction tree of the `zero` flag generator.

$$\text{Required Period} \ge T_{\text{comb\_max}} + T_{\text{input\_delay}} + T_{\text{output\_delay}} + T_{\text{uncertainty}}$$

Substituting the physical parameters for the Spartan-7 (`-1` speed grade) target device:
- **Worst-case combinational path delay ($T_{\text{comb\_max}}$):** $14.569\text{ ns}$
- **External input setup delay ($T_{\text{input\_delay}}$):** $2.000\text{ ns}$
- **External output delay ($T_{\text{output\_delay}}$):** $2.000\text{ ns}$
- **Clock uncertainty & jitter ($T_{\text{uncertainty}}$):** $0.025\text{ ns}$

$$\text{Period} \ge 14.569 + 2.000 + 2.000 + 0.025 = 18.594\text{ ns} \approx 18.6\text{ ns}$$

Setting the virtual clock period to **`20.000 ns`** (50 MHz) provides a safe timing budget with $\sim 1.4\text{ ns}$ of positive slack, preventing forced timing violations during synthesis and placement.

## Hardware Limitations & Bitstream Issues

While behavioral simulation, RTL synthesis, and implementation pass cleanly in Vivado, **Bitstream Generation fails** on the target hardware board.

### Pin Count Mismatch
- **Top-Level Interface Requirements:**
  - $A$: 32 pins
  - $B$: 32 pins
  - $alu\_op$: 4 pins
  - $Y$: 32 pins
  - $zero$: 1 pin
  - **Total Required I/O Pins:** $32 + 32 + 4 + 32 + 1 = 101\text{ pins}$

### Failure Cause
The selected target device (`xc7s50csga324-1`) on the Boolean board does not expose enough physical user-accessible I/O pins (switches, buttons, LEDs) to map 101 top-level signals concurrently. Because 96 pins remain unconstrained or map to invalid package locations, Vivado's Place & Route stage halts during bitstream assembly.

> **Note:** To run this ALU on actual hardware, wrap `alu_rv32i` inside a sequential top-level module (e.g., using UART, memory-mapped AXI registers, or time-multiplexed 7-segment displays) to reduce external pin requirements to clock, reset, and serial lines.

## Running the Project in Vivado

Follow these steps to set up, simulate, and synthesize the project in Xilinx Vivado:

### 1. Launch Vivado & Create Project
1. Open Vivado IDE.
2. Click **Create Project** $\rightarrow$ **RTL Project**.
3. Select target board/part: **Spartan-7 `xc7s50csga324-1`**.

### 2. Add Source Files
1. Add **Design Source**: `alu_rv32i.sv`.
2. Add **Simulation Source**: `tb_alu_rv32i.sv`.
3. Add **Constraints File**: `constraint_alu.xdc`.

### 3. Run Behavioral Simulation
1. In Flow Navigator, click **Simulation** $\rightarrow$ **Run Behavioral Simulation**.
2. Right-click `tb_alu_rv32i` and select **Set as Top** if prompted.
3. Observe signal waveforms for `A`, `B`, `alu_op`, `Y`, and `zero`.

### 4. Run Synthesis & Implementation
1. Set `alu_rv32i` as the synthesis top module.
2. Click **Run Synthesis** $\rightarrow$ verify netlist and timing reports.
3. Click **Run Implementation** to verify placed combinational logic and slack under the 20 ns virtual clock.
